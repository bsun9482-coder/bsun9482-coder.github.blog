## 第1章 阅读前说明：这本书怎样学

### 这本书会带你做出什么

如果你已经用 AI 聊过天，可能也想过：能不能让它读取一份指定资料，按要求查询，再把结果说清楚？本书就从这个具体目标开始。我们会逐步搭建一个小型数据分析助手，让它围绕一份练习表格回答问题，并把它接到网页中使用。

我们把这个助手叫作 DataAgent。它是本书学习项目的名字。书中数据均为虚构样本；每次增加功能，都要用这些样本检查结果。你会看到同一个项目怎样从第一次模型对话，逐渐具备查询、反馈和网页交互能力。

完成整条学习路线后，你应当能够运行这个项目、说明主要文件的用途，并根据实际现象检查问题：是模型没有接通，还是查询条件不对，或是网页没有收到结果。

### 怎样使用这本书

建议按章节顺序阅读，每次完成一个小任务。看到步骤时先操作，看到“应该得到什么”时再对照检查。屏幕没有出现预期结果，就停在当前步骤排查；先别继续复制后面的内容。

你可以让 AI 解释代码和报错，也可以请它复述某一段知识。向它提问时，说明自己正在做哪一步，附上实际操作和结果。我们最终检查的是电脑里的文件、程序返回的数据和网页上的行为。

这条路线分为四段：认识项目、跑通对话、接入业务、放到网页。每一段都有能看见的结果。

![OPEN-01-F01.webp](/images/build-your-first-ai-agent/OPEN-01-F01.webp)

图 0-1：先看懂目标，再逐步增加能力；每一段完成后都要检查结果。学习路线示意。

### 开始前需要具备什么

第一章只需要阅读一张小表格，并用纸笔或计算器核对几笔金额，不需要安装软件。进入第二章后，需要使用 Windows 或 macOS 电脑，能够新建文件夹、保存文件，并按书中的说明打开终端、输入命令。

后续程序使用 TypeScript 编写，并通过 Pi Agent 的 SDK 组织模型与工具调用。SDK 可以先理解为供程序使用的一组现成开发能力。你不必一开始就记住这些名字，第一次用到时会结合文件和操作解释。

调用在线模型需要相应的访问方式，可能产生按使用量计算的费用。具体选择、配置和检查放在首次对话章节。单独拥有某个聊天软件的会员，并不能据此判断本项目已经能调用对应的模型接口。

### 全书学习计划

本书按章更新。下面是完整学习计划；目前可以阅读“阅读前说明”和第一章，后面的章节随实际完成情况加入目录。

1. **先看懂成品**：用一份小表格，理解一次问题怎样变成有据可查的回答。
2. **准备环境**：建立练习目录，配置运行环境和模型，跑通第一次对话。
3. **认识项目结构**：分清模型、会话、工具和文件各自的用途，读懂第一次运行。
4. **设定角色**：写清助手的任务范围、回答要求和信息不足时的处理方式。
5. **接入数据**：编写查询工具，让助手根据条件读取样本、返回可核对的统计结果。
6. **补齐控制**：处理不合适的请求、工具错误和执行进度，检查成功与失败两条路径。
7. **接到网页**：显示流式回答和工具状态，加入停止操作，完成整个学习项目的验收。

### 怎样判断自己学会了

每章都保留一份简单记录：做了哪一步、预期是什么、实际是什么、哪里还没有通过。程序偶然回答正确一次，还不能说明它在换条件或出现错误时也能工作。

当你能够改变一个输入、先写下预期结果，再用实际输出验证自己的判断，就开始掌握这个项目了。需要查阅书中的写法很正常；更重要的是知道正在改什么，以及怎样检查有没有改对。

本书的基础目标是单用户学习项目。多用户账户、完整的生产运维和更深入的源码分析不属于这条入门路线。先把这一个助手做清楚、运行好，再决定是否继续扩展。

## 第2章 第一章｜先看懂成品：一次问题如何变成有据可查的回答

### 先确定本章的完成标志

开始写代码之前，先想清楚我们准备让程序做什么。这一章以一份只有六行的销售记录为例，走完“提出问题、确定条件、查询数据、检查结果、组织回答”的过程。

本章结束时，你应该能完成三件事：说清模型和查询工具分别负责什么；亲手核对一次查询的金额和记录条数；遇到条件不清楚、没有记录或查询失败时，知道助手应该怎样回答。

下面的对话和结构图都是教学示意。它们用来说明我们准备实现的行为，不是已经运行的网页截图，也不是一次真实模型调用的记录。本章暂时不用安装开发环境。

### 先看一个具体的使用场景

假设我们有一份销售记录，希望以后可以直接问助手：

> 请统计这份样本里，2026 年 9 月华东地区的销售金额，并告诉我一共用了几条记录。

一个符合要求的结果可以写成：

> 在这份样本中，2026 年 9 月华东地区共有 3 条匹配记录，金额合计 3,500 元。这是对当前样本的统计。

这里有四个需要检查的部分：时间是不是 2026 年 9 月，地区是不是华东，金额是不是 3,500 元，记录条数是不是 3 条。句子可以换一种说法，这四项含义应当一致。

从使用者的角度看，整个过程只有三个关键画面：提出带条件的问题、看到查询过程、读到带统计范围的回答。

![CH-01-F01.webp](/images/build-your-first-ai-agent/CH-01-F01.webp)

图 1-1：使用者提出条件，工具查询样本，助手说明结果和范围。预期交互示意。

### 认识这份练习数据

下面六行就是本章的全部数据。每一行代表一条记录；“金额”已经是该条记录的销售金额，单位为元。我们只做筛选和加总，不再计算单价乘数量，也不推断税费或利润。

| 编号 | 日期       | 地区 | 金额（元） |
| ---- | ---------- | ---- | ---------- |
| S01  | 2026-09-03 | 华东 | 1200       |
| S02  | 2026-09-08 | 华南 | 900        |
| S03  | 2026-09-11 | 华东 | 800        |
| S04  | 2026-09-18 | 华东 | 1500       |
| S05  | 2026-09-22 | 华北 | 600        |
| S06  | 2026-10-01 | 华东 | 2000       |

表格刻意保留了两个容易混淆的条件：S02 和 S05 的日期属于 9 月，但地区不同；S06 的地区是华东，但日期已经进入 10 月。只看地区或只看月份，都会得到另一个结果。

这些记录是为学习编写的虚构样本。它们不代表某家企业的完整业务，也不能用来推断真实市场表现。后面即使把它保存成文件，样本的含义也不会因此改变。

### 动手核对：先由你完成一次查询

#### 第一步，把条件从问题中找出来

拿一张纸，或者打开一个空白文本文件，写下这次问题的四项条件：

- **数据范围**：本章提供的六行样本。
- **日期范围**：2026 年 9 月 1 日到 9 月 30 日，包含首尾日期。
- **地区**：华东。
- **统计内容**：匹配记录的金额总和，以及匹配记录的条数。

把日期写完整，是为了避免把不同年份的 9 月混在一起。记录条数按实际行数计算，本章没有去重或合并订单的规则。

#### 第二步，保留同时满足条件的行

从 S01 开始逐行检查。日期和地区必须同时满足；只满足其中一个条件的行不计入。这一步应当留下 S01、S03、S04，共 3 条。

如果你留下了 S06，回到日期列检查；如果留下了 S02 或 S05，回到地区列检查。先检查筛选结果，再开始计算。

#### 第三步，加总并写清单位

打开电脑或手机里的计算器，输入 `1200 + 800 + 1500`，得到 `3500`。把结果记录为“3 条记录，合计 3,500 元”，不要只写一个没有含义的数字。

这次计算的依据很短：S01、S03、S04 对应的三笔金额相加，就是我们稍后检查程序的标准答案。

![CH-01-F02.webp](/images/build-your-first-ai-agent/CH-01-F02.webp)

图 1-2：只对同时满足日期与地区条件的三条记录加总。数据均为本章虚构样本。

#### 第四步，解释为什么其他行没有参加计算

用自己的话写两句说明：“S02、S05 地区不匹配；S06 日期不匹配。”能够解释排除原因，比只记住 3,500 这个答案更重要。以后换一份数据，筛选规则仍然要成立。

### 把刚才的手工过程交给程序

后面开发时，我们会把这套过程分给几个不同的角色。先理解各自的工作，不急着记代码名字。

- **模型**：理解用户想查什么，提出带参数的工具调用，并根据工具返回的信息组织回答。
- **Pi Agent 的运行流程**：衔接模型请求与工具执行，把工具结果带回后续模型调用，并提供执行过程中的事件。
- **查询工具**：一段由我们编写的程序，检查输入条件，读取约定的数据，筛选并计算。
- **数据文件**：保存原始记录。模型知道一个文件名，并不等于已经读到了文件内容。

在本项目里，加总金额的工作会放在查询工具中，方便重复运行和单独测试。模型拿到工具给出的金额、条数和统计范围，再把它们说明白。工具代码也可能写错，所以仍要用刚才的手算结果检查。

数据的关键往返是：模型提出查询，程序执行工具；工具把统计结果返回，模型再依据这个结果作答。

![CH-01-F03.webp](/images/build-your-first-ai-agent/CH-01-F03.webp)

图 1-3：模型提出调用，运行流程衔接执行，工具返回结果；箭头表示请求与结果的方向。简化结构示意。

这类助手通常称为 Agent，中文常说“智能体”。在本书的范围里，可以先把它理解为：模型参与决定下一步，程序提供工具并组织执行的助手。一个问题可能需要多次工具调用，也可能直接回答；图中只展示本例的一次查询。

### 工具到底接收什么，又返回什么

人可以读懂“帮我看看华东 9 月卖了多少”，程序更适合接收明确的字段。下面先用普通文字写一张“查询单”，帮助理解参数的作用；它不是现在需要运行的代码，也不是某个 SDK 接口格式。

```text
查询单
数据：本章销售样本
开始日期：2026-09-01
结束日期：2026-09-30
地区：华东
需要返回：金额总和、匹配条数、匹配记录编号
```

本项目计划让查询工具返回下面这些信息。返回原始编号，是为了让我们能回到表格复核；它不会凭空增加原始表格中没有的事实。

```text
查询结果
状态：查询成功
匹配记录：S01、S03、S04
记录条数：3
金额合计：3500
金额单位：元
统计范围：当前样本，2026 年 9 月，华东
```

模型最终可以把这些字段写成自然语言，但不应扩大统计范围。例如，把“样本中的华东记录”写成“公司华东地区全部营收”，就超出了我们提供的数据。

后面编写工具时，会把这张查询单落实成明确的参数结构，并给不支持的输入返回可理解的提示。这一章先掌握字段与原问题之间的对应关系。

### 三种情况，不能直接报一个金额

#### 条件没有说清楚

如果用户只说“华东卖了多少”，日期范围还不明确。助手可以继续询问“你想统计哪一个月，还是当前样本的全部日期？”等用户补全条件后再查询。本书采用先问清楚的做法，避免把自己的猜测当成用户要求。

#### 查询成功，但没有匹配记录

把地区改成“西南”，保留 2026 年 9 月这个条件，表格里没有匹配行。助手应该说明“当前样本中未找到符合条件的记录”。这只描述本次查询结果，不能据此断言现实中的西南地区当月销售额为零。

#### 查询根本没有完成

如果后面的程序找不到数据文件，或者读取时发生错误，就还没有得到有效的统计结果。此时应报告失败原因，先解决问题再重试。不能拿上一次查询的 3,500 元当成本次结果，也不能用零代替错误。

先分清“条件不足”“没有记录”和“执行失败”，再决定下一步怎么做。

![CH-01-F04.webp](/images/build-your-first-ai-agent/CH-01-F04.webp)

图 1-4：三种情况对应三种处理方式；没有记录与执行失败不能混为一谈。处理规则示意。

### 换一个条件，检查你是否真的理解了

先遮住下面的核对结果，仍然使用本章六行数据，独立完成三个小任务。每次写下筛选条件、保留的编号、金额和条数。

1. 查询 2026 年 9 月华南地区。
2. 查询华东地区在当前样本全部日期里的金额。
3. 查询 2026 年 9 月西南地区。

**核对结果**：第一题留下 S02，1 条，900 元。第二题留下 S01、S03、S04、S06，4 条，5,500 元。第三题没有匹配记录，回答时需要保留“当前样本”这个范围。

第二题比最开始多出 2,000 元，原因是日期范围放宽后计入了 S06。如果你得到的差值不同，先查保留的编号，不要只反复按计算器。

再想一个问题：“为什么华东销售下降了？”这份样本没有给出足够的对比周期和原因证据。助手应说明还缺少哪些信息，不能仅凭这六行记录补出一段经营分析。

### 保存你的第一份项目约定

用自己的文字保留下面五项约定，后面写代码时还会用到。可以记录在纸上，也可以放在一个普通文本文件中。

1. **目标**：根据明确的日期和地区，统计指定样本中的金额与条数。
2. **数据**：只使用约定的虚构销售记录；当前阶段不修改原始记录。
3. **正常结果**：包含统计范围、金额、单位、条数，并能按编号复核。
4. **特殊情况**：条件不足先询问，没有记录如实说明，查询失败先报告问题。
5. **验收样例**：2026 年 9 月华东应为 S01、S03、S04，共 3 条、3,500 元；换条件后重新核对。

你现在已经有了一个具体目标、一份输入样本和一组可以检查的结果。下一章进入环境准备，把第一次模型对话跑起来；今天保存的约定会继续作为后续开发的检查依据。

## 第3章 第二章｜准备环境：跑通第一次模型对话

### 这一章做到哪里，才算完成

第一章里，我们已经知道最终的助手要做什么。这一章先把最基础的一段路走通：在电脑上运行一段程序，把一句问题交给模型，再把回答显示在终端里。

本章的完成标志是：你能自己打开项目，运行命令，看到本次请求的模型名称、一句实际返回的中文回答，以及“本次对话完成。”。只有安装成功，或者看到“配置检查通过”，都还没有完成这次对话。

暂时不用让它计算销售额。第一章的数据查询会在后面的工具章节接入。本章中的程序每次启动都是一次新的对话，结束后不保留聊天历史。

下面以 Windows 的 PowerShell 终端为主线，macOS 的差异会在相应位置说明。图中的界面布局和终端内容均为教学示意；真实回答的措辞会变化，不需要与你看到的例句一字不差。

### 开始前，先准备三样东西

先把“写代码的软件”“运行代码的环境”和“提供回答的模型”分清楚。它们是三个不同的东西。

- **VS Code**：用来创建文件、编辑内容，也可以在里面打开终端。终端是输入命令的地方。
- **Node.js**：用来在电脑上运行本章程序。安装包附带 npm，它负责下载程序需要的依赖。
- **模型 API 账号与密钥**：用来让程序请求模型。本章用 DeepSeek 的 API 举例，需要你自己的有效密钥和可用额度。

在聊天网页里能正常聊天，不等于已经开通程序调用的 API，也不等于 API 免费。调用会按服务商的规则计费；先在控制台查看价格、余额和用量。本章只发送一句简短的练习问题，出现错误时先排查，不要连续反复运行。

我们使用 Node.js 24 LTS 这一版本系列，Pi SDK 固定为 `1.0.2`，tsx 固定为 `4.23.15`。本章编写时在 Windows x64、Node.js `24.14.0` 下检查安装与本地执行；macOS 的操作按官方安装说明整理，未在本轮实机验证。后续安装 Node.js 24 的维护更新即可，不必为了对齐截图专门安装旧补丁版。

### 第一步：安装软件，并检查终端

#### 下载 Node.js，选清系统与安装包

打开 [Node.js 下载页](https://nodejs.org/en/download)。选择 **24.x LTS**。LTS 表示长期支持版本；我们用这一系列建立本书的运行环境。

1. **Windows**：选择 Windows Installer（安装程序，`.msi`）。普通 Intel / AMD 电脑通常选 x64；如果“设置 → 系统 → 系统信息”显示 ARM 处理器，则选 ARM64。双击下载的文件，按安装向导完成安装，保留 npm 和 PATH 相关默认选项。
2. **macOS**：选择 macOS Installer（`.pkg`），按安装器提示完成。若下载页要求选架构，“关于本机”显示 Apple 芯片选 ARM64，显示 Intel 选 x64。
3. 安装完后，关闭已经打开的终端和 VS Code，再重新打开。旧窗口有时还没有读到新的程序路径。

如果这台电脑正在维护其他 Node.js 项目，先检查已有版本；不要为做练习随意替换别人正在使用的环境。已经是合适的 Node.js 24 版本，就直接进入检查步骤。

#### 安装 VS Code，找到“新建终端”

### 遇到问题，按报错所在的位置处理

#### 还没有开始请求模型

- **node / npm 找不到**：先确认安装完成，关闭并重开 VS Code。Windows 的 PowerShell 用 `npm.cmd`，不要为这一步随意修改系统执行策略。
- **ENOENT 或找不到 package.json**：终端所在的文件夹可能不对。重新在 VS Code 打开 hello-agent，再新建终端。
- **提示 .env 不存在**：确认它与 package.json 在同一层，文件名没有额外的 .txt；还要确认它已经保存。
- **提示填写 DEEPSEEK_API_KEY**：检查 .env 等号右边，不能留空，也不能仍是 paste-your-key-here。
- **JSON 解析错误**：回到 models.json，检查英文双引号、逗号、花括号是否完整。JSON 最后一项后面不要多加逗号。
- **找不到指定模型**：核对 book-deepseek 和 deepseek-flash 的拼写，确保与 hello.ts 完全对应。

#### 已经发起请求，但服务没有正常返回

- **401**：通常先检查 API 密钥是否正确、是否已撤销，以及是否来自同一家服务商；回到 API 控制台核对，不要用聊天网页的登录密码替代。
- **402**：检查 API 账号可用余额或额度；在明确收费方式后自行处理账户计费设置。
- **429**：查看服务商返回的具体提示，可能触发请求频率或其他额度限制。先停止重复提交，再按平台提示处理。
- **模型不存在或没有权限**：检查当前官方模型 ID 和账号权限。不要只换一个网上找到的名称就认定兼容。
- **连接失败或超过 60 秒**：检查网络是否能访问 API 域名，稍后重试；如果一直失败，保留报错文字和本次版本信息，逐项定位。

分享问题时，可以提供系统、Node.js 版本、执行的命令和错误文字。截图前遮住密钥、账号和其他无关个人信息；程序本身也会隐藏错误信息里完整出现的当前密钥，但不要因此省略检查。

先判断“命令还没跑起来”“配置没读对”还是“远端拒绝或超时”，再回到对应步骤。

## 第6章 第五章｜接入数据：写出第一把查询工具

### 一、本章要做出什么

### 三、先写查询函数：让计算可以单独检查

打开空白的 `sales-query.ts`。下面四段是同一个文件的四个组成部分，按顺序接在文件末尾，每段只粘贴一次，段与段之间留一空行。不要把后面的内容覆盖到前面的内容上。四段完成后再保存、运行。

#### 1. 定义查询条件和日期检查

先粘贴第一段。`Query` 描述查询条件，`Row` 描述一行记录。`validDate` 不只检查日期看起来像不像，还会检查日期实际是否存在，例如 2026 年没有 2 月 29 日。

```ts
import { readFile } from "node:fs/promises"

export type Query = { startDate: string; endDate: string; region: string }
type Row = { id: string; date: string; region: string; amount: number }

export function validDate(value: string) {
  if (!/^\d{4}-\d{2}-\d{2}$/.test(value)) return false
  const date = new Date(value + "T00:00:00Z")
  return (
    !Number.isNaN(date.getTime()) && date.toISOString().slice(0, 10) === value
  )
}
```

这里用完整的“年-月-日”，月份和日期补齐两位，例如 `2026-09-01`。所有日期都保持这个格式后，后面的字符串比较才能正确表达先后关系。代码里的 UTC 只用于核对日期，不会把表格改成带时区的订单时间。

#### 2. 把一行文字转成记录

把第二段接在第一段后面。它把一行 CSV 按逗号分成四项，检查编号、日期、地区和金额，再把金额从文字转为数字。如果坏行被直接跳过，统计可能少算却仍显示成功，所以这里发现不合格式的行就停止并报出行号。

```ts
function parseRow(line: string, index: number): Row {
  const cells = line.split(",")
  const [id, date, region, money] = cells
  if (
    cells.length !== 4 ||
    !id ||
    !validDate(date) ||
    !region?.trim() ||
    !/^\d+$/.test(money) ||
    !Number.isSafeInteger(Number(money))
  ) {
    throw new Error(`样本第 ${index + 2} 行格式不对，请对照原表。`)
  }
  return { id, date, region, amount: Number(money) }
}
```

`Number.isSafeInteger` 用来检查金额是否在 JavaScript 可精确表示的整数范围内。这个练习只计算整数元；实际项目若有小数金额，需要另行约定精度与单位，不能把本例直接当成完整财务计算方案。

#### 3. 读取固定文件并检查表头

第三段继续接在末尾。文件路径固定指向本代码旁边的 `sales-sample.csv`，没有把任意文件路径作为参数交给模型。文件打不开、表头不一致、没有数据行或编号重复，都应当报错。

```ts
async function loadSales() {
  let text: string
  try {
    text = await readFile(
      new URL("./sales-sample.csv", import.meta.url),
      "utf8"
    )
  } catch {
    throw new Error("无法读取 sales-sample.csv，请检查文件名、位置和读取权限。")
  }
  const [header, ...lines] = text
    .replace(/^\uFEFF/, "")
    .trim()
    .split(/\r?\n/)
  if (header !== "编号,日期,地区,金额（元）" || lines.length === 0) {
    throw new Error("样本表头不对或没有数据，请恢复本章提供的样本。")
  }
  const rows = lines.map(parseRow)
  if (new Set(rows.map((row) => row.id)).size !== rows.length) {
    throw new Error("样本出现重复编号，请对照原表。")
  }
  return rows
}
```

`new URL(..., import.meta.url)` 表示从当前代码文件的位置找到样本。它不依赖你临时把终端切到了哪个文件夹。开头去掉的 BOM 是部分 UTF-8 文件可能带的标记，不是销售内容。

#### 4. 同时按日期和地区筛选，再加总

最后接上第四段并保存。`filter` 保留同时满足三项比较的行；`reduce` 从零开始，把这些行的金额依次相加。开始日期和结束日期都包含在查询范围里。

```ts
export async function querySales(query: Query) {
  const { startDate, endDate, region } = query
  if (
    !validDate(startDate) ||
    !validDate(endDate) ||
    startDate > endDate ||
    !region.trim()
  ) {
    throw new Error("请填写有效的起止日期和地区；开始日期不能晚于结束日期。")
  }
  const rows = await loadSales()
  const matched = rows.filter(
    (row) =>
      row.date >= startDate && row.date <= endDate && row.region === region
  )
  const totalYuan = matched.reduce((sum, row) => sum + row.amount, 0)
  if (!Number.isSafeInteger(totalYuan))
    throw new Error("合计超出本例可精确计算的整数范围。")
  return {
    status: matched.length ? "ok" : "no_records",
    scope: "本书虚构销售样本",
    startDate,
    endDate,
    region,
    count: matched.length,
    totalYuan,
    unit: "元",
    ids: matched.map((row) => row.id),
  }
}
```

返回对象里，`totalYuan` 是金额合计，`count` 是条数，`ids` 是原始记录编号。`status` 为 `ok` 表示有匹配记录，`no_records` 表示文件读完且筛选完成，但没有匹配行。遇到前面的错误时，程序会抛出错误，不会返回一个伪装成成功的零元结果。

以九月华东为例，S02、S05 的地区不匹配，S06 的日期不匹配。剩下三行的金额相加，才得到 3,500 元。

### 三、先把限制写成可以单独检查的函数

#### 1. 检查日期与地区

打开 `query-policy.ts`，粘贴下面第一段。它接收待检查的条件，有问题时返回原因，没有问题时返回 `undefined`，表示这一层允许继续。

```ts
import { validDate } from "./sales-query.js"

export function queryBlockReason(input: unknown): string | undefined {
  if (!input || typeof input !== "object") return "请提供查询条件。"
  if (
    !("startDate" in input) ||
    !("endDate" in input) ||
    !("region" in input)
  ) {
    return "请补齐开始日期、结束日期和地区。"
  }
  const { startDate, endDate, region } = input
  if (
    typeof startDate !== "string" ||
    typeof endDate !== "string" ||
    typeof region !== "string" ||
    !region.trim() ||
    !validDate(startDate) ||
    !validDate(endDate) ||
    startDate > endDate
  ) {
    return "日期或地区不正确，请使用有效日期并确认先后顺序。"
  }
  const days =
    (Date.parse(endDate + "T00:00:00Z") -
      Date.parse(startDate + "T00:00:00Z")) /
      86_400_000 +
    1
  if (days > 31) return "本例每次最多查询 31 个自然日，请缩小日期范围。"
  return undefined
}
```

这里复用第五章的 `validDate`，没有重新编一套日期判断。起止日期都检查有效后，才计算包含首尾的天数；末尾的 `+ 1` 很重要。例如 9 月 1 日到 9 月 1 日算一天，不是零天。

`86_400_000` 是一天的毫秒数。我们把两个日期都当作 UTC 零点进行相减，这里处理的是样本中的日期范围，没有把真实订单时间混进来。9 月 1 日到 9 月 30 日为 30 天，到 10 月 1 日为 31 天，到 10 月 2 日就超过本例限制。

`unknown` 表示暂时不知道传进来的值是什么，必须先检查才能读取字段。正常工具调用还会经过 SDK 的参数检查，这个独立函数也保留基本检查，方便离开模型单独测试。字段类型正确，并不代表日期范围就符合业务约定。

#### 2. 检查问题是否为空或过长

把下面第二段接在同一个文件末尾，保留第一段，然后保存。

```ts
export function checkQuestion(question: string) {
  if (!question.trim())
    throw new Error("问题不能为空，请填写 sales-question.txt。")
  if (question.length > 1000)
    throw new Error("本例问题长度最多 1000，请精简后再试。")
}
```

这里的 `question.length` 按 JavaScript 字符串的 UTF-16 码元计数，不是模型 token 数，也不完全等于人眼看到的字符数；部分表情会占两个。对本章的普通中文问题，先理解为一项简单的长度限制即可，不用把它当成费用计算公式。

#### 3. 用边界值验证限制

打开 `check-controls.ts`，粘贴下面完整内容并保存。检查里特意保留“正好 31 天”和“多一天”、“正好 1000”和“多一个”这两组边界。

```ts
import assert from "node:assert/strict"
import { queryBlockReason, checkQuestion } from "./query-policy.js"

const base = { startDate: "2026-09-01", endDate: "2026-09-30", region: "华东" }
assert.equal(queryBlockReason(base), undefined)
assert.equal(queryBlockReason({ ...base, endDate: "2026-10-01" }), undefined)
assert.match(queryBlockReason({ ...base, endDate: "2026-10-02" }) ?? "", /31/)
for (const input of [
  null,
  {},
  { ...base, startDate: "2026-02-30" },
  { ...base, startDate: "2026-10-01" },
  { ...base, region: " " },
]) {
  assert.ok(queryBlockReason(input))
}
checkQuestion("请查询九月华东的样本。")
checkQuestion("问".repeat(1000))
assert.throws(() => checkQuestion("问".repeat(1001)), /1000/)
assert.throws(() => checkQuestion("  "), /不能为空/)
console.log("控制规则检查通过；没有调用模型，也没有读取样本。")
```

## 第8章 第七章｜接到网页：流式回答、停止与验收

### 一、这一章要把什么接起来

到第六章为止，你已经可以在终端里向助手提问，让它调用查询工具，看到结果、错误和停止原因。这一章把同一个助手接到浏览器：在输入框里写问题，点击发送，看到处理过程和逐段出现的回答，需要时点击停止。

先认清三处位置：浏览器负责输入和显示；你电脑上的 Node 程序负责调用模型、执行工具；在线模型服务负责理解问题和组织回答。CSV 仍由本地程序读取，工具结果会随模型请求发送给服务商。本书只使用虚构样本，不把真实业务数据直接放进练习。

这三处通过请求和响应连接。网页不会直接读取密钥，也不会自己计算销售统计。

### 四、把运行过程转换成网页能读的消息

打开 web-run.ts。本文件接收三个东西：问题、停止信号、发送消息的函数。它不需要知道按钮长什么样，只负责运行助手，把有用事件交给网页。

#### 1. 约定本例的消息格式

先写入下面两段。WebEvent 是本例自己的消息类型，不是 SDK 自带的网页接口。status 表示进度，delta 是新增文字，tool 是工具记录，error 是失败提示，reset 清空回答区，done 则表示这一次后台流程已经收尾。

**web-run.ts · 第 1 / 6 段**

```ts
import { openWebSession } from "./web-session.js"

export type WebEvent =
  | { type: "status" | "delta" | "tool" | "error"; text: string }
  | { type: "reset" }
  | { type: "done"; state: "finished" | "stopped" | "failed"; text: string }
type Send = (event: WebEvent) => void
```
